# Development Workflow

## 标准流程

```text
Idea → RFC → PRD → Architecture → Task → Codex → Review → Merge
```

每阶段保留关联记录；未完成前一阶段的关键确认，不进入依赖该结论的下一阶段。文档任务可将多个阶段写在同一任务记录中，但需明确目标、边界、验收和审查结论，无需虚构设计材料。

## 阶段与交付要求

| 阶段 | 责任 | 输入与工作 | 交付与进入下一阶段的条件 |
| --- | --- | --- | --- |
| Idea | 提出者 | 描述问题、价值及与项目目标的关系 | 记录范围、非目标和待回答问题，维护者同意继续讨论 |
| RFC | 提出者与审查者 | Request for Comments：比较方案、约束及取舍 | 形成讨论结论，明确采纳、修改或拒绝的方案 |
| PRD | 需求负责人 | Product Requirements Document：将采纳方案转成需求 | 明确场景、功能边界、非功能要求及可验证验收标准 |
| Architecture | 架构负责人或维护者 | 定义模块职责、依赖、接口边界和风险 | 形成设计说明；重要选择写入 ADR，并获得审查确认 |
| Task | 维护者 | 把设计拆成可独立验证的工作项 | 每项有范围、依赖、允许修改区域、验收方法和提交要求 |
| Codex | 执行代理 | 阅读仓库规则，在授权任务范围内实施 | 交付可审查差异、相关文档和真实验证结果，列明未决事项 |
| Review | 维护者或指定审查者 | 核对需求、设计、范围、证据与文档 | 问题解决后明确接受；未通过则退回相应阶段 |
| Merge | 有合并权限的维护者或获授权执行者 | 核对已接受的变更和检查结果 | 按任务约定提交或合并，确认目标分支与提交记录，更新变更日志 |

角色可由同一维护者承担，但自动生成的内容不能替代明确的审查结论。合并权限与自动化执行权限由维护者授权。

## 记录位置与关联

- Idea、RFC、PRD：放在 docs/product/ 或关联的 Issue 中，记录状态并更新索引。
- Architecture：放在 docs/architecture/；关键决策使用 decisions/ 下的 ADR。
- Task：使用 Issue 或 docs/sprints/ 下的迭代记录，关联上游需求和设计。
- Codex、Review、Merge：在任务或 Pull Request 中记录差异、检查证据、评审结论和最终提交标识。
- Alpha 的推进或退役决定另记入 [decision/](../../decision/README.md)，代码合并不等于 Alpha 获准上线。

普通新文档使用小写 kebab-case 名称；项目章程 PROJECT_CHARTER.md 与本流程 DEVELOPMENT_WORKFLOW.md 是指定的治理文档名称。记录保留稳定编号或链接，避免复制多份互相冲突的需求。

## 范围与变更处理

需求变化时先更新对应 RFC、PRD 或架构决策，再调整 Task；执行者不能自行扩大范围。Review 发现问题应记录原因、修复要求和重新验证结果，不跳过未解决的问题进入 Merge。

当前 Sprint 0.2 是已授权的目录与文档任务：只创建和完善工程说明，不开发交易代码，不增加运行依赖。维护者已明确要求以一次指定 commit 交付，执行者按该任务约定直接提交；后续任务遵循各自授权的分支与合并方式。

## 验证与完成标准

- 文档任务检查目录 README 覆盖、相对链接、命名、范围及内容一致性。
- 代码任务在后续获得授权后执行相应测试；当前没有测试套件，不能声称业务测试通过。
- 提交前审查完整差异，确认不包含敏感信息或无关修改。
- 提交后核对提交信息、文件清单、父提交及目标分支；报告验证结果与遗留事项。
