# AI Alpha OS MVP 产品需求文档

版本：第一版（V1）

所属任务：Sprint 1.1 - Define AI Alpha OS MVP Product Requirement

状态：产品需求定义；功能尚未开发，验收尚未执行。

本次交付仅为需求文档。后续依据本 PRD 完成 Architecture 与 Task 拆分，再实施和验证；文档完成不代表 MVP 已完成。

## 一、项目目标

AI Alpha OS 是一个以长期稳定盈利为最高目标的 A股量化交易系统。

第一阶段目标不是自动交易，而是建立以下完整闭环：

```text
数据 → 分析 → 信号 → 模拟交易 → 结果反馈 → 策略优化
```

长期稳定盈利是项目目标，当前没有已验证的盈利结果。第一阶段通过历史验证和模拟交易积累可追溯的证据，支持规则评估与策略优化。

## 二、MVP核心目标

第一版系统只验证：

**是否可以通过数据和规则发现具有历史有效性的Alpha。**

系统应能记录验证过程与结论，包括未发现有效 Alpha 的结果。历史有效性不等同于未来盈利；不能将完成系统功能验收直接表述为证明盈利能力。

## 三、V1系统范围

### 1. 市场状态分析

功能包含：

- 情绪周期。
- 涨停数量。
- 连板高度。
- 炸板率。
- 市场成交额。

输出用于市场复盘和 Alpha 分析，应保留分析日期、数据范围和指标口径。各指标的具体定义、统计范围及异常数据处理方式在后续设计中明确。

### 2. Alpha评分系统

第一批包含：

- 竞价强度。
- 板块强度。
- 龙头强度。
- 情绪修复。
- 首板二进。

系统应根据可解释的数据与规则形成评分，用于候选股票筛选与模拟交易信号生成。每项评分应能追溯输入、触发规则及规则版本。

上述名称定义首批研究与评分范围，不预设已验证有效的交易规则。计算公式、权重、阈值和历史有效性评价口径在后续任务中定义并审查，本 PRD 不编写策略实现。

### 3. 回测系统

要求支持：

- 历史数据验证。
- 买卖规则模拟。
- 收益统计。
- 最大回撤统计。
- 胜率统计。

回测记录应关联数据范围与版本、买卖规则版本、模拟条件及结果。信号计算只能使用当时可获得的数据，避免使用未来信息。

模拟交易与历史回测的成交、费用、持仓和交易约束口径，以及各项统计指标的计算口径，需要在实施前明确。结果须可复现，并区分历史回测结果与每日模拟交易结果。

### 4. 决策记录系统

每一次信号必须记录：

| 字段 | 要求 |
| --- | --- |
| decision_id | 每次信号的唯一标识，用于关联后续模拟交易和反馈 |
| 时间 | 信号生成时间，保留交易日期与时区语义 |
| 股票代码 | 能唯一识别市场内证券的代码 |
| 输入数据 | 信号生成时使用的数据快照或可追溯的版本引用 |
| 触发规则 | 触发信号的规则及版本，说明触发原因 |
| 评分结果 | 本次 Alpha 评分结果及可解释的分项依据 |
| 最终结果 | 关联模拟交易结果与评价状态，并保留更新记录 |

信号刚生成时，最终结果可标注为“待评估”；后续应更新为已评估、未成交或无法评估等明确状态，并记录原因。不得在结果尚未产生时填写虚构收益，也不得覆盖原始输入、规则和评分以改变历史记录。

### 5. 实施前需明确的边界

- A股股票池、历史样本区间、数据来源、授权和更新时点。
- 市场状态指标及五类 Alpha 评分的定义、版本和缺失数据处理。
- 回测与模拟交易的规则、成交假设、费用及评价口径。
- 历史有效性的评价方法、对照基准、样本划分和判定条件。
- 数据存储、模块接口与执行方式，由后续 Architecture 定义。

以上是实施前的待决事项，不增加 V1 业务范围，也不在本次任务中选择技术栈或开发代码。

## 四、V1暂不开发内容

暂时不开发：

- 自动实盘交易。
- 100个虚拟游资竞技场。
- 大模型训练。
- 高频交易。

原因：**先完成盈利闭环验证。**

本阶段以数据、规则、历史验证和模拟交易支持闭环，不接入实盘自动执行。已有 arena/ 等目录属于工程结构预留，不表示相关功能属于 V1 或已经实现。

## 五、用户使用流程

目标使用者为进行市场复盘、Alpha 研究和模拟验证的项目使用者。

### 收盘后

```text
数据更新
    ↓
市场复盘
    ↓
Alpha分析
    ↓
生成候选股票
```

收盘后产生的候选股票供下一交易日开盘前分析使用。

### 开盘前

```text
竞价分析
    ↓
生成模拟交易信号
```

使用当时已可获得的竞价数据，结合候选股票生成信号并写入决策记录。竞价数据可用时点与截点由后续数据规范明确，不能将尚未产生的数据用于信号生成。

信号产生后，按预先定义的模拟规则记录模拟成交、未成交和持仓变化，供盘后评价；不提交实盘订单。

### 盘后

```text
统计结果
    ↓
更新策略表现
```

盘后结果通过 decision_id 关联原始信号；未结束的模拟持仓保留待评估状态。复盘结论进入下一轮研究与策略优化，规则调整需版本化，不能追溯修改已生成信号。

收盘后与盘后均属于当日收盘后的工作：前者准备下一交易日候选，后者评价已有信号和模拟交易结果。

## 六、成功验收标准

MVP完成必须满足以下五项，全部为待实施、待验证的验收条件：

| 序号 | 验收标准 | 验证方式与证据 |
| --- | --- | --- |
| 1 | 数据可以正常进入系统 | 在约定的数据范围内完成导入或更新，能查询记录及来源；缺失、重复或异常数据有明确处理记录 |
| 2 | Alpha指标可以计算 | 五类 Alpha 评分均有明确口径，可在已知输入上计算并核对结果，输入与规则版本可追溯 |
| 3 | 策略可以回测 | 按事先定义的买卖规则完成历史模拟，保存运行条件、模拟交易记录和结果，可重复验证 |
| 4 | 每次决策可以追踪 | 每个信号具有唯一 decision_id，并完整保留时间、股票代码、输入数据、触发规则、评分结果和最终结果状态 |
| 5 | 结果可以统计分析 | 可输出收益、最大回撤和胜率统计，结果能关联回测或模拟交易记录；无有效样本时明确标记不可计算，不伪造数值 |

还需展示一次端到端流程：数据进入系统 → 市场状态分析 → Alpha 评分 → 候选股票与信号 → 模拟交易 → 结果统计 → 形成下一轮策略优化记录。优化结论可以是保留、修改或否决规则，不要求为了完成验收而宣称策略有效。

具体样本、评价周期、有效性阈值和计算容差须在对应开发任务开始前确定。技术闭环验收与 Alpha 历史有效性结论分别记录；本 PRD 不设定未经验证的收益目标。
